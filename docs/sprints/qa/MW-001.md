## Observações (não bloqueiam, mas a PO deveria saber)

1. **JSON malformado ou com tipo errado volta 400 sem mensagem em português.** Exemplos: `amount: "abc"`, `amount: 1e30`, `category: 5`, `description: 5`, corpo `not json`, corpo vazio ou `[]`. Em Production a resposta é `400` **com corpo vazio**. Em Development ela traz o stack trace em inglês. Para reproduzir: `curl -i -X POST localhost:5215/api/expenses -H 'Content-Type: application/json' -d '{"amount":"abc","description":"x","category":"food"}'`. O front sempre manda um número, então o usuário não chega a esse caso. Se chegasse, veria a mensagem genérica "Não foi possível registrar o gasto. Tente de novo.". Isso não fere nenhum critério escrito, mas vale uma história técnica sobre o contrato de erro.
2. **Valor muito grande.** Não existe teto de valor. `1e30` passa na validação do front e é recusado pela API (estouro de `decimal`) com 400 sem mensagem, então o usuário vê a mensagem genérica. Fica para a PO decidir se quer um limite.
3. **Valor como string é aceito.** `"amount":"10.5"` → 201, porque o padrão web do System.Text.Json lê números a partir de string. É inofensivo, mas é mais permissivo do que o contrato documentado ("número").
4. **Zeros à direita voltam como foram enviados.** `10.990` é aceito, o que está certo (o valor tem 2 casas), mas a resposta devolve `"amount":10.990` com 3 dígitos. O front formata com 2 casas, então não aparece para o usuário. Pode importar para a listagem e os totais (MW-002 a MW-004).
5. **Datas extremas aceitas** (`0001-01-01`, `9999-12-31`). Isso está conforme a história ("qualquer data válida é aceita"). Fica registrado para quando a PO tratar datas.
6. **Descrição sem limite de tamanho.** Não há critério sobre isso. Fica para a PO avaliar.
7. **"Hoje" na API é a data local do servidor.** O front sempre envia a data do formulário, que é a data local do navegador. Só um cliente que omita `date` depende do fuso do servidor. A decisão está documentada em "Decisões do Dev".
8. **`launchSettings.json` ainda aponta `launchUrl: "weatherforecast"`**, que veio do template. Não faz parte desta história, é só limpeza.
9. **Processo:** o `ci.yml` não roda em push de branch de feature. Por isso a evidência automatizada da API só aparece quando o PR é aberto. Sugiro ao Scrum Master abrir o PR e conferir o job `api` antes de pedir o merge.
